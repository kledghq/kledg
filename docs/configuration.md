# Configuration

Toutes les variables sont listées dans [`.env.example`](../.env.example).

| Variable | Obligatoire | Description |
| --- | --- | --- |
| `DATABASE_URL` | Oui | Connexion PostgreSQL utilisée par l'application (avec pooling sur Neon). Replis : `POSTGRES_URL`, `POSTGRES_PRISMA_URL`, puis `POSTGRESQL_ADDON_URI` (module PostgreSQL de Clever Cloud lié à l'application). |
| `DATABASE_URL_UNPOOLED` | Recommandé | Connexion directe, utilisée par les migrations. Repli : `POSTGRES_URL_NON_POOLING`, puis `DATABASE_URL`. |
| `DATABASE_MIGRATION_URL` | Non | Connexion directe du rôle propriétaire du schéma, pour les migrations et `pnpm db:rls-role`, quand l'application se connecte avec un autre rôle. Prioritaire sur `DATABASE_URL_UNPOOLED`. |
| `KLEDG_RLS` | Non | Isolation des sociétés dans la base (sécurité au niveau des lignes de PostgreSQL) : `off` (par défaut) ou `enforce`. Avec `enforce`, chaque requête porte l'utilisateur ou la tâche qui agit, et la base refuse les lignes des autres sociétés même si une requête oublie son filtre. Exige le rôle applicatif créé par `pnpm db:rls-role` ; toute autre valeur arrête le serveur à la première requête. Voir [rls.md](rls.md). |
| `KLEDG_DATABASE_URL` | Non | Connexion de l'application avec le rôle applicatif de `KLEDG_RLS=enforce`. Prioritaire sur `DATABASE_URL`, qui garde alors le rôle propriétaire (variable gérée par l'intégration Neon sur Vercel, par exemple). |
| `KLEDG_APP_DB_PASSWORD` | Non | Mot de passe du rôle applicatif pour `pnpm db:rls-role`, à défaut de l'option `--password`. |
| `DATABASE_SSL` | Non | `false` désactive TLS vers la base, `true` le force. Par défaut : TLS, sauf pour `localhost`, un nom sans point (service Docker `db`, URL interne Render `dpg-...-a`) et les réseaux privés chiffrés par l'hébergeur (`*.railway.internal`, `*.flycast`, `*.internal`). `sslmode=disable` ou `sslmode=require` dans l'URL priment. |
| `DATABASE_POOL_MAX`, `DATABASE_POOL_IDLE_TIMEOUT_MS` | Non | Taille du pool de connexions par instance du serveur (défaut 10) et durée après laquelle une connexion inutilisée est fermée, en millisecondes (défaut 5000 sur Vercel, 30000 ailleurs). Sur Vercel, l'instance attend que ces connexions inutilisées soient fermées avant d'être suspendue (`attachDatabasePool`). Sur Neon, gardez l'URL avec pooling dans `DATABASE_URL`. Ailleurs, gardez `DATABASE_POOL_MAX` multiplié par le nombre d'instances sous la limite de connexions de votre offre PostgreSQL, en laissant de la marge pour les migrations et `pg_dump`. |
| `BETTER_AUTH_SECRET` | Oui | Secret de signature des sessions (32 caractères minimum). La clé qui chiffre les identifiants bancaires en est dérivée, sauf avec `ENCRYPTION_KEY`. Pour le changer sans reconnecter les banques, voir [Changer le secret](#changer-le-secret). |
| `BETTER_AUTH_SECRETS` | Non | Rotation du secret, au format de Better Auth : secrets versionnés séparés par des virgules, le secret courant en premier (`2:<nouveau>,1:<ancien>`). Les anciens servent seulement à relire ce qu'ils ont chiffré. |
| `BETTER_AUTH_URL` | Selon l'hébergeur | URL publique de l'instance. Par défaut, l'URL fournie par l'hébergeur : URL de production Vercel, `RAILWAY_PUBLIC_DOMAIN`, `RENDER_EXTERNAL_URL`, `https://<FLY_APP_NAME>.fly.dev`, `COOLIFY_URL`. Obligatoire sur Clever Cloud, avec Docker Compose et avec `pnpm start`. Avec un domaine personnalisé, définissez-la : l'URL de l'hébergeur reste acceptée pour la connexion. |
| `ADMIN_EMAIL` | Oui, jusqu'à la création du premier compte | Seul email autorisé à créer le premier compte administrateur sur `/setup`. Sans `SETUP_TOKEN`, c'est aussi l'adresse qui reçoit le lien d'installation. |
| `SETUP_TOKEN` | Non | Sans lui, `/setup` accepte le jeton dérivé de `BETTER_AUTH_SECRET` (HMAC-SHA256 de `kledg:setup-token:v1`, en base64url) que le guide de déploiement de kledg.com calcule dans le navigateur, et, avec `ADMIN_EMAIL` et `RESEND_API_KEY`, un lien à usage unique envoyé à `ADMIN_EMAIL`, valable 30 minutes (seule son empreinte SHA-256 est stockée, dans la table `verification`). Défini, il l'emporte et devient le seul jeton accepté par `/setup` (ouvrez `/setup?token=<valeur>` ou saisissez-le dans le formulaire), au moins 16 caractères. Sans lui, `/setup` refuse de créer le compte administrateur : sinon la première personne à ouvrir l'URL d'une instance fraîchement déployée en deviendrait administrateur. `ADMIN_EMAIL` n'est pas un secret et ne le remplace pas. Générez-le avec `openssl rand -base64 24` ; il peut être supprimé une fois l'administrateur créé. |
| `RESEND_API_KEY` | Recommandé | Envoi des emails. Sans clé, les emails sont écrits dans les logs. |
| `EMAIL_FROM` | Avec Resend | Expéditeur, sur un domaine vérifié dans Resend. |
| `ENCRYPTION_KEY` | Non | Chiffrement des identifiants bancaires (64 caractères hexadécimaux). Défaut : dérivée de `BETTER_AUTH_SECRET`. |
| `CRON_SECRET` | Recommandé | Protège `/api/cron/*`. Vercel l'envoie automatiquement aux tâches planifiées. Sans lui, les routes restent appelables par tous, donc bridées : la synchronisation bancaire ne traite que les intégrations non synchronisées depuis 20 heures, au plus 4 fois par jour pour toute l'instance, la clôture automatique des périodes tourne au plus 2 fois par jour, et elles ne répondent que des nombres. |
| `LOGO_ALLOWED_HOSTS` | Non | Hôtes autorisés pour un logo de société donné par URL (`https`, séparés par des virgules). Vide par défaut : le logo doit être importé comme image. |
| `TRUST_PROXY_HOPS` | Recommandé hors Vercel | Nombre de reverse proxies (1 à 10) placés devant Kledg qui ajoutent chacun l'adresse vue à `X-Forwarded-For` (nginx `$proxy_add_x_forwarded_for`, Caddy, Traefik). L'adresse du client est la N-ième en partant de la droite ; ce qui est à sa gauche a été envoyé par le client et est ignoré. Sans cette variable (ni Vercel, ni `RATE_LIMIT_IP_HEADER`), Kledg ne fait confiance à aucun en-tête : `X-Real-IP` et `X-Forwarded-For` peuvent être forgés par le client, et Next.js ne donne pas l'adresse de la connexion aux routes. Les limites par adresse IP sont alors partagées par tous les clients (un avertissement est écrit dans les journaux) et le journal d'audit n'enregistre pas d'adresse. N'activez pas cette variable si le port de Kledg est joignable sans passer par le proxy. Valeur pour chaque hébergeur : [self-hosting.md](self-hosting.md#adresse-ip-des-clients). |
| `RATE_LIMIT_IP_HEADER` | Non | En-tête unique posé par votre proxy avec l'adresse du client (par exemple `CF-Connecting-IP`), à la place de `TRUST_PROXY_HOPS`. Le proxy doit écraser toute valeur envoyée par le client. Sur Vercel, l'adresse vient de `x-vercel-forwarded-for`, posé par la plateforme. |
| `RATE_LIMIT_DISABLED` | Non | `true` désactive la limitation des tentatives (tests locaux uniquement). |
| `QONTO_API_URL` | Non | URL de base de l'API Qonto (une API compatible : proxy, API simulée de test). Défaut : `https://thirdparty.qonto.com/v2`. |
| `QONTO_ENVIRONMENT` | Non | `sandbox` pour utiliser le bac à sable Qonto (`https://thirdparty-sandbox.staging.qonto.co/v2`) avec une clé API du bac à sable. Défaut : production. |
| `QONTO_STAGING_TOKEN` | Non | Jeton du bac à sable Qonto (portail développeur, *Sandbox access*), envoyé dans l'en-tête `X-Qonto-Staging-Token`. Obligatoire avec `QONTO_ENVIRONMENT=sandbox`. |
| `REVOLUT_ENVIRONMENT` | Non | `sandbox` pour utiliser le bac à sable Revolut Business (tests). Défaut : production. |
| `REVOLUT_API_URL`, `REVOLUT_CONSENT_URL` | Non | Remplacent l'URL de l'API et de la page d'autorisation Revolut Business. |
| `PONTO_API_URL` | Non | URL de base de l'API Ponto. Défaut : `https://api.myponto.com`. |
| `NEXT_PUBLIC_DISABLE_SW` | Non | `true` désactive le service worker de l'application installable : les navigateurs qui l'avaient installé le désinscrivent et suppriment ses caches à la visite suivante. Lue à la construction (`pnpm build`) : reconstruisez puis redéployez après l'avoir changée. Voir [self-hosting.md](self-hosting.md#application-installable). |
| `KLEDG_COMMIT`, `KLEDG_VERSION` | Non | Commit et version affichés sur la page **Mises à jour** (arguments de construction de l'image Docker, voir [self-hosting.md](self-hosting.md#docker)). Le commit déployé fourni par l'hébergeur passe avant : `VERCEL_GIT_COMMIT_SHA`, `RAILWAY_GIT_COMMIT_SHA`, `RENDER_GIT_COMMIT`, `CC_COMMIT_ID` (Clever Cloud), `SOURCE_COMMIT` (Coolify). |
| `KLEDG_DEPLOYS_FROM_GITHUB` | Non | `true` quand l'hébergeur redéploie l'instance à chaque fusion sur la branche principale du dépôt GitHub (Fly.io avec GitHub Actions, Clever Cloud ou Coolify reliés à GitHub, webhook Dokploy) : la page **Mises à jour** propose alors la mise à jour en deux clics. Automatique sur Vercel, et sur Railway et Render quand le déploiement vient d'un commit. `false` la désactive partout. |
| `SKIP_MIGRATIONS`, `KLEDG_BACKUP`, `KLEDG_BACKUP_DIR`, `KLEDG_BACKUP_KEEP` | Non | Image Docker : ne pas migrer au démarrage, ne pas sauvegarder la base avant une migration (`off`), dossier et nombre de sauvegardes gardées. Voir [self-hosting.md](self-hosting.md#docker). |

## Changer le secret

Si `BETTER_AUTH_SECRET` a pu être lu par quelqu'un d'autre, remplacez-le :

1. Générez un nouveau secret (`openssl rand -base64 32`).
2. Définissez `BETTER_AUTH_SECRETS=2:<nouveau secret>` et gardez l'ancien dans `BETTER_AUTH_SECRET`, puis redéployez.
3. Au démarrage, Kledg chiffre de nouveau avec le nouveau secret les identifiants bancaires et le jeton GitHub chiffrés avec l'ancien (`lib/crypto/reencrypt.ts`) ; le journal du serveur indique combien de valeurs ont été traitées. Toutes les sessions se ferment : chacun se reconnecte.
4. Une fois ce démarrage passé, mettez le nouveau secret dans `BETTER_AUTH_SECRET`, supprimez `BETTER_AUTH_SECRETS` et redéployez : l'ancien secret ne sert plus à rien.

Avec `ENCRYPTION_KEY`, les identifiants bancaires ne dépendent pas du secret : il suffit de le remplacer.

## Ancien format de chiffrement

Les secrets stockés (identifiants bancaires de `bank_connections.secretKeyEncrypted` et des champs secrets de `integrations.credentials`, jeton GitHub de `update_connections.tokenEncrypted`) sont chiffrés en AES-256-GCM (`lib/integrations/encryption.ts`). Depuis la version qui suit 0.3.1, ils sont scellés au format v2 (préfixe `v2:`, liés à leur ligne et à leur champ par des données authentifiées : une valeur copiée dans une autre ligne ne s'ouvre plus). L'ancien format (sans préfixe, sans lien à la ligne) est encore lu, et chaque valeur lisible est scellée de nouveau en v2 à chaque démarrage du serveur (`reencryptStoredSecrets`, `lib/crypto/reencrypt.ts`).

**Le lecteur de l'ancien format est supprimé dans Kledg 0.4** : une valeur restée dans l'ancien format ne s'ouvrira plus, et la banque ou GitHub concerné devra être reconnecté. Avant de passer en 0.4 :

1. Vérifiez qu'il ne reste rien : au démarrage, le journal du serveur avertit (`Secrets in the legacy encryption format: N ...`) tant qu'il reste des valeurs, et la page **Configuration** (administrateurs de l'instance) affiche « Ancien format de chiffrement » avec leur nombre. Rien ne s'affiche quand tout est au format v2.
2. Pour les sceller de nouveau, redémarrez le serveur, ou lancez `pnpm secrets:reencrypt` avec l'environnement de l'instance (`DATABASE_URL`, `BETTER_AUTH_SECRET` ou `ENCRYPTION_KEY`, et `BETTER_AUTH_SECRETS` pendant une rotation) : le script fait le même passage, affiche ce qui reste et sort avec le code 1 s'il reste des valeurs dans l'ancien format. Il est idempotent.
3. Une valeur qui reste après ce passage ne s'ouvre avec aucune des clés configurées (secret perdu, `ENCRYPTION_KEY` changée) : reconnectez la banque concernée, ou GitHub dans **Mises à jour**. La nouvelle connexion est scellée en v2.

`countLegacySecrets` (`lib/crypto/reencrypt.ts`) ne lit que le format des valeurs : aucune clé n'est nécessaire pour le compte.

## Sécurité

- **Premier compte** : `/setup` exige une preuve de propriété de l'instance : `SETUP_TOKEN` s'il est défini (il l'emporte toujours), sinon un lien à usage unique envoyé à `ADMIN_EMAIL` (avec `RESEND_API_KEY`). Sans l'un ni l'autre, la page reste bloquée. Le lien pointe vers l'URL configurée de l'instance, jamais vers l'en-tête `Host`, et un nouveau lien n'est pas envoyé moins d'une minute après le précédent. Seul `ADMIN_EMAIL` peut créer le compte. La création est atomique : deux envois simultanés ne peuvent pas créer deux administrateurs.
- **Limitation des tentatives** : connexion, réinitialisation de mot de passe, `/setup` et enregistrement de clients OAuth sont limités par adresse IP (pour toutes ces limites, celles de Better Auth comprises, une adresse IPv6 compte pour son préfixe /64, que détient un seul abonné, et une adresse IPv4 écrite en IPv6 compte comme l'adresse IPv4) ; changement d'adresse ou de mot de passe, suppression de compte, gestion des utilisateurs, appels aux banques et à GitHub, imports, exports et contrôle total MCP sont limités par utilisateur ou par société (`RATE_LIMITS`, `lib/rate-limit.ts`). Les compteurs sont dans la base de données (table `rateLimit`), ce qui fonctionne aussi sur plusieurs instances serverless.
- **Requêtes** : les routes de Kledg lisent le corps des requêtes en le comptant (1 Mo par défaut pour du JSON, 20 Mo pour les fichiers, 3 Mo pour la fiche société et son logo), et répondent 413 au-delà, même sans `Content-Length`. Sur Vercel, la plateforme limite déjà toute requête à 4,5 Mo. Une requête qui modifie des données avec le cookie de session doit venir de l'instance (`Origin`, `Sec-Fetch-Site`) et être en JSON, ou en `multipart/form-data` pour les fichiers (415 sinon). Les classeurs `.xlsx` sont décompressés sous un budget de 200 Mo (10 000 fichiers au plus, taux de compression de 100 au plus au-delà de 10 Mo) avant d'être lus.
- **En-têtes HTTP** : toutes les réponses portent `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin` (l'origine seule, même entre les pages de l'instance : l'adresse d'une page ne part jamais dans un référent), `Strict-Transport-Security`, `Cross-Origin-Opener-Policy: same-origin` et une `Permissions-Policy` restrictive (`lib/security-headers.ts`, `next.config.ts`). Les pages ont une Content-Security-Policy à nonce, nouveau à chaque requête (`proxy.ts`) : aucun script sans le nonce, aucun cadre, aucun objet. Les réponses de l'API ont une CSP qui n'autorise rien, sauf les fichiers (relevés, pièces) que l'application affiche dans ses propres pages.
- **Application installable** : le service worker (`public/sw.js`, portée `/`) ne met en cache que la page hors ligne, les icônes et les fichiers de construction à empreinte (`/_next/static/`). Il ne touche jamais `/api/*`, les pages connectées, les données des composants serveur (`?_rsc=`) ni les requêtes autres que GET ou d'une autre origine : aucune donnée comptable n'est stockée sur l'appareil. Les navigations passent par le réseau ; sans réseau, la page « Vous êtes hors ligne » s'affiche. Chaque construction installe un nouveau worker qui supprime les caches de la précédente. La déconnexion supprime les fichiers de construction mis en cache (la page hors ligne et les icônes, publiques, restent) et envoie `Clear-Site-Data: "cache"` pour vider le cache HTTP du navigateur. Le manifeste, le worker et la page hors ligne sont servis sans session et ont leur propre CSP (le worker : scripts de l'instance uniquement ; la page hors ligne : aucun script).
- **Sociétés** : seul un administrateur de l'instance peut supprimer une société, et seulement si elle n'a ni écriture validée ni exercice clôturé (la base le refuse aussi) ; sinon il l'archive : lecture seule, masquée des listes, restaurable depuis la page Sociétés. Suppression, archivage et restauration sont tracés.
- **Journal d'audit** : en ajout seul. La base refuse toute modification ou suppression d'une entrée (déclencheur `audit_logs_append_only`), sauf la purge des entrées de plus de 10 ans par la fonction `kledg_purge_audit_logs(date)`, à appeler depuis une console SQL avec le rôle propriétaire de la base (le rôle applicatif ne peut pas l'exécuter) : `SELECT kledg_purge_audit_logs(now() - interval '10 years');`. Le propriétaire de la base peut toujours désactiver un déclencheur : protégez ses identifiants.
- **Sessions** : Better Auth garde la session dans un cookie signé mis en cache 60 secondes (`session.cookieCache`, `lib/auth.ts`), mais Kledg vérifie à chaque requête, par une lecture indexée, que la session existe toujours en base, que le compte n'est pas bloqué et quel est son rôle (`getCurrentUser`, `lib/session.ts`) : une déconnexion d'un autre appareil, une réinitialisation ou un changement de mot de passe, un blocage ou un retrait du rôle d'administrateur s'appliquent immédiatement aux pages et aux routes de Kledg. Seul l'endpoint de lecture de Better Auth (`/api/auth/get-session`, affichage du nom dans l'interface) peut encore présenter une session révoquée pendant au plus 60 secondes. La réinitialisation du mot de passe déconnecte toutes les sessions du compte ; le changement de mot de passe déconnecte les autres sessions, sauf si l'utilisateur décoche l'option. L'accès aux sociétés (membres) est relu en base à chaque requête. Les assistants (MCP) n'utilisent pas de cookie.
- **Rôles** : `companyAdmin` (tout, y compris identifiants bancaires, paramètres et suppression de la société), `accountant` (écritures, plan comptable, journaux, règles, exercices, clôture, rapprochement, exports), `viewer` (lecture seule). Les membres sont gérés par les administrateurs de l'instance.

### Isolation des sociétés dans la base

Avec `KLEDG_RLS=enforce`, PostgreSQL applique lui-même la séparation des sociétés : l'application se connecte avec un rôle qui n'est pas propriétaire des tables, chaque transaction indique qui agit (utilisateur, assistant limité aux sociétés autorisées, tâche planifiée limitée à sa société) et les politiques de la base ne laissent lire ou écrire que les lignes des sociétés accessibles. Une écriture sans contexte est refusée. Mise en place : [self-hosting.md](self-hosting.md#isolation-des-sociétés-dans-la-base-rls) ; fonctionnement et limites : [rls.md](rls.md).

## Personnaliser une instance

Une instance dérivée (un fork) peut restreindre des actions, ajouter un bandeau, une carte sur `/login` ou un panneau sur les pages d'une société sans modifier le reste du code : voir [extension-points.md](extension-points.md). Kledg n'en utilise aucun par défaut.
